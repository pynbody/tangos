.. _histograms:

Histories between snapshots
===========================

A merger history from :ref:`time_series` has one point per snapshot, and a
simulation's snapshots are often hundreds of Myr apart. Some quantities change much
faster than that -- star formation rates and black hole accretion rates above
all -- yet the simulation holds enough information to recover them in between:
every star particle records when it formed. *Histogram properties* store such a
history in fine time bins. This tutorial shows how they are stored, what that
means when you read them, and how the built-in ``SFR_histogram`` is written, so
that you can write one of your own.

.. note:: Before you start, make sure tangos is installed and can find the
 tutorial database; :ref:`installation` covers both. The examples query it, and
 need no simulation files. You should have read :ref:`time_series`, which
 introduces ``SFR_histogram`` and reads it back, and :ref:`custom_properties`.

.. ipython::

 In [1]: import tangos

 In [2]: import pylab as p

Chunks, not whole histories
---------------------------

Each snapshot could store the whole star formation history of each halo up to
that time, but that would store the early history over and over again. Instead,
each snapshot stores only a *chunk*: the history since the previous snapshot. The
``raw()`` live calculation shows what is actually stored at one snapshot,
without any further processing:

.. ipython::

 In [1]: chunk = galaxy.calculate(lambda: raw(SFR_histogram))

 In [2]: len(chunk)

That is 25 bins of 20 Myr, or 0.5 Gyr. The chunk reaches back to the previous
snapshot, 0.43 Gyr earlier, and always covers at least 0.5 Gyr; at the first
snapshot, it covers the whole history up to that time. Successive chunks
therefore tile the whole history.

When you read the property normally, tangos *reassembles* the chunks: it walks
back along the merger tree, collecting each progenitor's chunk, and joins them
into one history. ``reassemble(SFR_histogram, 'place')`` puts this snapshot's
chunk alone on the same time axis as the full history, which shows how little
of it is stored here:

.. ipython::

 In [1]: sfr = galaxy["SFR_histogram"]

 In [2]: this_chunk = galaxy.calculate(lambda: reassemble(SFR_histogram, 'place'))

 In [3]: t = galaxy.get_objects("SFR_histogram")[0].x_values()

 In [4]: p.figure()

 In [5]: p.plot(t, sfr, label="reassembled history");

 In [6]: p.plot(t, this_chunk, ':', label="stored at this snapshot");

 In [7]: p.xlabel("t/Gyr"); p.ylabel(r"SFR/$M_{\odot}\,{\rm yr}^{-1}$"); p.legend();

``x_values()`` gives the time at the start of each bin, in Gyr. It belongs to the
stored property object, which
:meth:`~tangos.core.halo.SimulationObjectBase.get_objects` returns, rather than to
the value.

The raw chunk is in solar masses per *Gyr*, a thousand million times the values
plotted: the reassembly converts to solar masses per year as it goes. This
is a historical choice, and invisible unless you read the raw values.

Which progenitors are counted
-----------------------------

By default the chunks are collected along the major progenitor branch only. To
add up the chunks of every progenitor instead, use ``reassemble(SFR_histogram,
'sum')``; :ref:`time_series` compares the two for this galaxy.

The merger tree, though, is only known at the snapshots. Within the last
interval -- here, after the penultimate snapshot at 2.82 Gyr -- there are no
earlier progenitors to add, so the two reassemblies are necessarily identical
there, whatever really happened:

.. ipython::

 In [1]: sfr_all = galaxy.calculate(lambda: reassemble(SFR_histogram, 'sum'))

 In [2]: last_interval = t > 2.82

 In [3]: (sfr_all[last_interval] == sfr[last_interval]).all()

The closer together the snapshots, the shorter this final interval. It rarely
matters for science, but is worth knowing when you look at the most recent few
hundred Myr of a history.

How ``SFR_histogram`` is written
--------------------------------

A histogram property is a class derived from
:class:`~tangos.properties.TimeChunkedProperty`, which handles storing chunks and
reassembling them. This is the class behind ``SFR_histogram``, from
``tangos/properties/pynbody/SF.py``:

.. literalinclude:: ../../tangos/properties/pynbody/SF.py
   :language: python
   :pyobject: StarFormHistogram

``calculate`` works as for any property that uses particle data (see
:ref:`custom_properties_particles`): it receives the halo's particles, here with
pynbody. It bins the formation times of the halo's stars into a histogram of the
*whole* history, in bins of ``self.pixel_delta_t_Gyr``, and then returns only
the slice that ``self.store_slice(t_now)`` selects -- the chunk described above.
To write your own histogram property, follow the same pattern: compute the full
history up to the current time, and return ``M[self.store_slice(t_now)]``.

``reassemble`` is optional. ``StarFormHistogram`` overrides it only to convert
units after the chunks are joined; the joining itself is inherited.
``plot_xlabel`` and ``plot_ylabel`` label the plots that the web interface
draws.

.. warning::

   :class:`~tangos.properties.TimeChunkedProperty` finds the previous snapshot in
   its ``preloop`` method. If your class overrides ``preloop``, call
   ``super().preloop(...)`` from it, or only the last 0.5 Gyr before each
   snapshot is stored, leaving gaps in the history.

Changing the time resolution
----------------------------

Bins are 20 Myr wide unless the simulation says otherwise. To use 10 Myr bins for
every histogram property of a simulation, set its ``histogram_delta_t_Gyr``
property *before* the first ``tangos write`` of any histogram:

.. code-block:: python

   sim = tangos.get_simulation("my_simulation")
   sim["histogram_delta_t_Gyr"] = 0.01

Changing it after histograms have been written leaves chunks of two resolutions
in the database, which cannot be reassembled consistently. To change it, delete
the histogram properties first (see :doc:`/how-to/managing_a_database`).
