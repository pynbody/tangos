.. _custom_properties:

Writing your own properties
===========================

tangos comes with properties for the quantities most people need -- masses,
profiles, images, star formation histories (``tangos list-possible-properties``
lists them all). Sooner or later you will want one of your own. This tutorial
shows how to write one, in two kinds:

* a *live* property, calculated on the fly from values already in the database,
  whenever you ask for it;
* a property calculated from the *particle data*, which ``tangos write`` stores
  in the database alongside the built-in ones.

.. note:: Before you start, make sure tangos is installed and can find the
 tutorial database; :ref:`installation` covers both. Everything up to
 :ref:`custom_properties_particles` runs against that database, with no
 simulation files. The last part writes to a database built from simulation
 data, as in :doc:`/tutorials/first_database`.

.. ipython::

 In [1]: import tangos

 In [2]: halo = tangos.get_object("tutorial_changa/%960/halo_1")

 In [3]: timestep = halo.timestep

The simplest property
---------------------

A property is a python class derived from
:class:`~tangos.properties.PropertyCalculation`. It names the property it
provides, and calculates its value in a ``calculate`` method:

.. ipython::

 In [1]: from tangos.properties import PropertyCalculation

 In [2]: class ExampleHaloProperty(PropertyCalculation):
    ...:     names = "myproperty"
    ...:
    ...:     def calculate(self, particle_data, existing_properties):
    ...:         return 42.0
    ...:

This property is ``42.0`` for every object. It needs nothing from the
simulation, so you can use it straight away, as a live calculation (see
:ref:`calculating`):

.. ipython::

 In [1]: halo.calculate(lambda: myproperty())

 In [2]: values, = timestep.calculate_all(lambda: myproperty())

 In [3]: len(values), values[:5]

The brackets matter: ``myproperty()`` asks tangos to *calculate* the property
now, where a bare ``myproperty`` would look for a value stored in the database,
and find none. Nothing is stored by a live calculation.

The class's own name is not important; ``names`` is what tangos goes by. The two
arguments to ``calculate`` are the particle data, which a live property is not
given (it is ``None``), and the object's existing properties, used next.

Making tangos find your properties
----------------------------------

Here the class was defined in the python session that uses it. To use it
anywhere else -- in another session, in the web interface, or in ``tangos write``
-- put it in a python module of its own, such as ``mytangosproperty.py``, in a
folder on your python path. Then tell tangos to import that module, by setting
an environment variable before starting python, the web server or any ``tangos``
command:

.. code-block:: bash

   export TANGOS_PROPERTY_MODULES=mytangosproperty

Separate several modules with commas. If tangos cannot import a module you name,
it carries on without it, and without any visible warning: the first sign is
that a property you wrote is unknown. If that happens, check that ``import
mytangosproperty`` works in python by itself.

If your properties are part of a package you install with pip, you can register
the module with an *entry point* instead, and leave the environment alone. In the
package's ``pyproject.toml``:

.. code-block:: toml

   [project.entry-points."tangos.property_modules"]
   mytangosproperty = "mytangosproperty"

.. versionadded:: 1.0.10
   The ``tangos.property_modules`` entry point.

.. warning::

   After changing a property class, restart python (or the web server) before
   using it again. tangos keeps using the first class it found for each property
   name for the rest of the session, so reloading the module, or defining the
   class again, has no effect.

Properties calculated from other properties
-------------------------------------------

A live property becomes useful when it works from what is already stored. This
one returns the *x* coordinate of a halo's centre, from the ``shrink_center``
property that :doc:`/tutorials/first_database` calculates:

.. ipython::

 In [1]: class ExampleXProperty(PropertyCalculation):
    ...:     names = "my_x"
    ...:
    ...:     def calculate(self, particle_data, existing_properties):
    ...:         return existing_properties['shrink_center'][0]
    ...:
    ...:     def requires_property(self):
    ...:         return ["shrink_center"]
    ...:

``existing_properties`` behaves like the object itself: index it with the name of
a stored property to get its value. ``requires_property`` lists the properties
``calculate`` reads. When tangos calculates over many objects at once, it fetches
everything they need in a few large database queries rather than one per
object, and it can only do that if it knows in advance what to fetch:

.. ipython::

 In [1]: halo['shrink_center'][0]

 In [2]: halo.calculate(lambda: my_x())

 In [3]: x, = timestep.calculate_all(lambda: my_x())

 In [4]: len(x)

Without ``requires_property``, ``halo.calculate`` would still work, but
``timestep.calculate_all`` would fail with ``KeyError: "No such property
'shrink_center'"``.

Only 53 of the timestep's 719 objects have a value: those without a stored
``shrink_center`` cannot be calculated, so they are left out, as any
failed calculation is (see :ref:`time_series`).

Several values at once
----------------------

Closely related values are often easiest to calculate together. Give ``names``
several names and return a value for each, in the same order:

.. ipython::

 In [1]: class ExampleYZProperty(PropertyCalculation):
    ...:     names = "my_y", "my_z"
    ...:
    ...:     def calculate(self, particle_data, existing_properties):
    ...:         centre = existing_properties['shrink_center']
    ...:         return centre[1], centre[2]
    ...:
    ...:     def requires_property(self):
    ...:         return ["shrink_center"]
    ...:

 In [2]: halo.calculate(lambda: my_y()), halo.calculate(lambda: my_z())

 In [3]: halo['shrink_center']

Each name is used on its own, as before; tangos calls ``calculate`` once and keeps
both values.

Properties that need the particle data
--------------------------------------

Most properties worth having have to be calculated from the simulation itself.
This one is the one-dimensional velocity dispersion of a halo's particles:

.. literalinclude:: ../examples/mytangosproperty.py
   :language: python
   :start-at: import numpy

Save it as ``mytangosproperty.py``, in a folder on your python path.

Deriving from :class:`~tangos.properties.pynbody.PynbodyPropertyCalculation`
rather than :class:`~tangos.properties.PropertyCalculation` says two things: the
property needs the particle data, and that data is loaded by pynbody, so
``particle_data`` is a pynbody snapshot of the halo's particles. (yt has an
equivalent, and so can a handler of your own; see :doc:`/how-to/custom_handlers`.)

tangos never loads particle data during a live calculation -- in an analysis
session it would almost never be what you want -- so a property like this cannot
be calculated on the fly. Even with the module imported, asking for it fails:

.. ipython::

 In [1]: import mytangosproperty

 In [2]: try:
    ...:     halo.calculate(lambda: velocity_dispersion())
    ...: except NameError as error:
    ...:     print(error)
    ...:

A live calculation only considers classes that need no particle data, so it
reports the property as unknown -- the same message a module that failed to
import would give, though here the import worked.

Instead, ``tangos write`` calculates the property for every halo and stores the
result. Set ``TANGOS_PROPERTY_MODULES`` as above, and from the shell run:

.. code-block:: bash

   tangos write velocity_dispersion --for tutorial_changa

Everything :doc:`/tutorials/first_database` showed for the built-in properties
applies to yours: ``--include-only`` to choose objects, ``--with-prerequisites``,
running in parallel (:doc:`/how-to/parallel`). Your class need know nothing
about any of these; it is always given the particles of the one halo it is
calculating for.

Results are committed every few minutes, so you can look at them before the
command finishes. ``velocity_dispersion`` is then a stored property like any
other: ``halo["velocity_dispersion"]`` for one halo, or
``timestep.calculate_all("velocity_dispersion")`` for all of them. pynbody hands
tangos particle data in physical units -- kpc, km/s, Gyr -- so the velocity
dispersion is in km/s. ``calculate`` returns a plain ``float``: tangos stores
numbers and numpy arrays, but not the units pynbody attaches to them.

   :doc:`/tutorials/histograms`, the next tutorial, for properties that record a
