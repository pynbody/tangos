Supported simulation formats
============================

tangos reads raw simulation output through an *input handler*: a small class
that knows what a given code's snapshots look like on disk, which halo finder
produced the catalogues beside them, and how to hand both to pynbody or yt.
The table below lists every combination of simulation code and halo finder
that tangos ships a handler for, and what each one needs beyond
``tangos add``.

You rarely name a handler yourself. ``tangos add`` starts from the class you
give it -- :class:`~tangos.input_handlers.pynbody.PynbodyInputHandler` if you
give none -- and then picks whichever of its subclasses matches the most files
in the folder, so a directory of Gadget snapshots next to SubFind catalogues
selects :class:`~tangos.input_handlers.pynbody.GadgetSubfindInputHandler`
without being asked. The **handler string** column below records the value you
must pass when that guess cannot be made: the yt handlers, because the yt
module is not imported unless requested, and a few ChaNGa variants that are
deliberately excluded from auto-detection. (You may need to scroll the table
horizontally to see all the columns.)

**Groups** says whether the format has a two-level FoF-group/subhalo hierarchy,
which you populate with a second pass of each command carrying ``--type
group``. Where it says no, that is not the same as "no substructure": AHF and
AdaptaHOP subhalos are ordinary halo-type objects joined to their host by
``parent`` and ``child`` links, which arrive with the finder properties rather
than needing a pass of their own.

``tangos link`` derives the merger tree itself, by matching particles between
consecutive snapshots with pynbody's bridge. The three ``import-`` commands
instead read a tree the finder or a tree-builder already wrote, which is faster
and, for consistent-trees, richer -- it carries *phantom* halos, objects the
finder lost at one step and recovered at the next. Where the table offers both,
either works.

Combinations that need more than the common path
------------------------------------------------

Every combination starts with ``tangos add <folder>``; most then take one
``tangos import-properties`` pass and one merger-tree command. The exceptions,
and the exact property names each finder wants, are below.
:doc:`/tutorials/first_database` is the full walkthrough, with these same
commands in context; this page is the summary you come back to.

ChaNGa + AHF
~~~~~~~~~~~~

The finder properties come from AHF's ``.AHF_halos`` files, read by
:class:`~tangos.input_handlers.halo_stat_files.AHFStatFile`, and you name the
columns you want:

.. code-block:: bash

   tangos add tutorial_changa
   tangos import-properties Mvir Rvir --for tutorial_changa
   tangos link --for tutorial_changa

The companion run with black holes takes the same three commands, then three
more: :class:`~tangos.input_handlers.changa_bh.BHLogData` and its subclasses
read ChaNGa's ``.shortened.orbit`` and ``.mergers`` logs, and the black holes
they find become objects with their own typetag.

.. code-block:: bash

   tangos import-changa-bh --sims tutorial_changa_blackholes
   tangos write BH_mass BH_mdot_histogram --for tutorial_changa_blackholes --type bh
   tangos crosslink tutorial_changa tutorial_changa_blackholes

Note that ``tangos crosslink`` takes two positional simulation names rather
than ``--for``.

Gadget + SubFind
~~~~~~~~~~~~~~~~

This is the combination with a group hierarchy, so both the property import and
the tree building run twice. Naming no properties imports every column the
catalogue offers, which is what the group pass needs: it is the pass that
brings in each group's ``child`` halos, while the halo pass brings in each
halo's ``parent`` group.

.. code-block:: bash

   tangos add tutorial_gadget --min-particles 100
   tangos import-properties --for tutorial_gadget
   tangos import-properties --type group --for tutorial_gadget
   tangos link --for tutorial_gadget
   tangos link --type group --for tutorial_gadget

Gadget + Rockstar
~~~~~~~~~~~~~~~~~

Rockstar's own columns live in ``out_<n>.list``, read by
:class:`~tangos.input_handlers.halo_stat_files.RockstarStatFile`, and the tree
comes from consistent-trees. There is no ``tangos link`` step:

.. code-block:: bash

   tangos add tutorial_gadget_rockstar --min-particles 100
   tangos import-properties Mvir Rvir X Y Z --for tutorial_gadget_rockstar
   tangos import-consistent-trees --for tutorial_gadget_rockstar

:class:`~tangos.input_handlers.consistent_trees.ConsistentTrees` expects
``trees/tree_0_0_0.dat``, ``outputs/scales.txt`` and
``outputs/really_consistent_<n>.list`` inside the simulation folder, or inside
a ``halos/`` subfolder of it. Add ``--with-ids`` if you want each halo's
consistent-trees identifier stored as a property as well.

Gadget + AHF
~~~~~~~~~~~~

AHF can build its own merger trees, and ``tangos import-ahf-trees`` reads the
resulting ``AHF_mtree`` files; see AHF's documentation for the toolbox that
produces them.

.. code-block:: bash

   tangos add tutorial_gadget_ahf --min-particles 100
   tangos import-properties Mvir Rvir Xc Yc Zc --for tutorial_gadget_ahf
   tangos import-ahf-trees --for tutorial_gadget_ahf

Unlike the ChaNGa case above, this handler reads the finder properties from
pynbody's AHF catalogue rather than from a stat file. That distinction shows up
if you name no properties at all: the positions and velocities are then
imported as the vector properties ``shrink_center`` and ``bulk_velocity``, and
``Xc``, ``Yc``, ``Zc``, ``VXc``, ``VYc`` and ``VZc`` are skipped. Naming them
explicitly, as above, still imports them individually.

Gadget-4 + SubFind
~~~~~~~~~~~~~~~~~~

``tutorial_gadget4`` here is the integration test's fixture, not a dataset you
can download. As for Gadget + SubFind, both
property passes are needed for the group hierarchy:

.. code-block:: bash

   tangos add tutorial_gadget4
   tangos import-properties --for tutorial_gadget4
   tangos import-properties --type group --for tutorial_gadget4

Gadget-4 writes merger trees as it runs, and
:class:`~tangos.tools.subfind_merger_tree_importer.SubfindTreeImporter` can
read them instead of rebuilding the tree from particles:

.. code-block:: bash

   tangos import-subfind-trees --for tutorial_gadget4

``tangos link --for tutorial_gadget4`` remains the alternative. Neither is
exercised by ``build.sh``, which stops after the property imports for this
dataset, so treat both as untested here.

Gadget-4 + HBT+
~~~~~~~~~~~~~~~

HBT+ tracks each subhalo through time itself and gives it a ``TrackId``, so
``tangos link`` does no particle matching at all for this format:
:meth:`~tangos.input_handlers.pynbody.Gadget4HBTPlusInputHandler.match_objects`
simply pairs equal track ids. That makes the link step cheap, and it runs
before the property imports:

.. code-block:: bash

   tangos add tutorial_gadget4_hbtplus
   tangos link --for tutorial_gadget4_hbtplus
   tangos import-properties --for tutorial_gadget4_hbtplus
   tangos import-properties --type group --for tutorial_gadget4_hbtplus

The snapshots live in the ``tutorial_gadget4`` folder and the HBT+ catalogues
in ``tutorial_gadget4_hbtplus``, so you need both unpacked. Both are integration
test fixtures rather than downloadable datasets.

RAMSES + HOP
~~~~~~~~~~~~

HOP writes no statistics file, so there is nothing for
``tangos import-properties`` to read and the step is simply absent; tangos
enumerates the halos through pynbody's HOP catalogue instead. Halo numbering
starts at zero, and ``--no-renumber`` keeps it that way rather than
renumbering from one in order of decreasing particle count:

.. code-block:: bash

   tangos add tutorial_ramses --min-particles 100 --no-renumber
   tangos link --for tutorial_ramses

Everything you subsequently ask for -- masses, positions, profiles -- is
computed by ``tangos write`` from the particles.

RAMSES + AdaptaHOP
~~~~~~~~~~~~~~~~~~

There is no stat file here either, but the catalogue itself carries
precomputed quantities, so ``tangos import-properties`` with no names does
useful work: it brings in AdaptaHOP's own columns, plus ``parent``, ``child``,
``shrink_center``, ``bulk_velocity`` and ``contamination_fraction``, the last
computed from the contamination counts if AdaptaHOP stored them.

Enzo + Rockstar, through yt
~~~~~~~~~~~~~~~~~~~~~~~~~~~

``enzo.tinycosmo`` is the integration test's fixture, not a dataset you can
download.

yt is not imported unless you ask for it, so this combination always names a
handler; ``yt.YtInputHandler`` is enough, because the subclass is then chosen
from the files present. You import properties twice, the second pass asking for
:class:`~tangos.input_handlers.halo_stat_files.RockstarStatFile`'s derived
physical-unit columns:

.. code-block:: bash

   tangos add enzo.tinycosmo --handler=yt.YtInputHandler --min-particles 100
   tangos import-consistent-trees --for enzo.tinycosmo --with-ids
   tangos import-properties Mvir Rvir X Y Z VX VY VZ --for enzo.tinycosmo
   tangos import-properties Mvir_Msun Rvir_kpc X_Mpc Y_Mpc Z_Mpc --for enzo.tinycosmo

EAGLE, and ChaNGa through yt
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

These two have pages of their own, because what differs is the data rather than
the command sequence: :doc:`/how-to/eagle` covers the EAGLE directory layout and
the registration needed to download the particle data, and :doc:`/how-to/yt`
covers reading a ChaNGa+AHF run with yt in place of pynbody.


Your combination is not listed
------------------------------

Write a handler. This is a smaller job than it sounds, because a new handler
inherits nearly everything: of the fifteen pynbody-based
handlers bundled in ``tangos/input_handlers/``, eight are under twenty lines
including the class statement, and
:class:`~tangos.input_handlers.pynbody.GadgetAHFInputHandler` is three: the
class statement and two class attributes, with no methods at all.

What a new handler has to provide depends on how much of the work pynbody
already does for you.

*If pynbody reads both your snapshots and your catalogues*, subclass
:class:`~tangos.input_handlers.pynbody.PynbodyInputHandler` and you usually
need only:

* ``patterns`` -- the glob patterns that recognise a snapshot in the simulation
  folder, such as ``["snapshot_???"]``; and, optionally,
  ``auxiliary_file_patterns``, files that are not snapshots but whose presence
  identifies the format, such as Rockstar's ``["halos_*.bin"]``. These two
  attributes are what auto-detection scores, and for several handlers they are
  the entire subclass.
* ``pynbody_halo_class_name``, if pynbody would otherwise choose the wrong
  catalogue class for the folder.
* ``_is_able_to_load``, if the patterns alone let through files you cannot
  actually read -- typically a two-line try/except around a pynbody load.

*If your finder writes a text catalogue tangos does not know*, add a
:class:`~tangos.input_handlers.halo_stat_files.HaloStatFile` subclass: a
``filename`` classmethod that maps a snapshot path to the catalogue path, and a
``_column_translations`` dict for columns whose names or units differ from what
tangos expects. Handlers find it automatically -- ``HaloStatFile`` dispatches to
whichever subclass can load the file -- so you need only set
``halo_stat_file_class_name`` if two of them could both claim it. This is what
makes ``tangos import-properties`` work at all for your format.

*If pynbody cannot read your data*, subclass
:class:`~tangos.input_handlers.HandlerBase` directly and implement
``enumerate_timestep_extensions``, ``enumerate_objects``,
``load_timestep_without_caching`` and ``load_object``, plus ``match_objects`` if
you want ``tangos link`` to work. :doc:`/custom_input_handlers` walks through
exactly this, with a runnable toy handler, and
:class:`~tangos.input_handlers.yt.YtInputHandler` is the real-world example.

It is worth exploring the bundled handlers to see more complex cases. 
:class:`~tangos.input_handlers.pynbody.ChangaInputHandler` spends most of its
118 lines parsing ChaNGa parameter files and logs to recover simulation
metadata; :class:`~tangos.input_handlers.eagle.EagleLikeInputHandler` spends
165 on a directory layout that splits particles from catalogues and on
reconstructing unique subgroup identifiers;
:class:`~tangos.input_handlers.ramsesHOP.RamsesAdaptaHOPInputHandler` spends 157
translating a catalogue's precomputed quantities into tangos properties and
links; and :class:`~tangos.input_handlers.yt.YtInputHandler` spends 179 doing
without pynbody entirely. A format with a tidy directory layout, a readable
catalogue and metadata in the snapshot header is more likely to be a handful 
of lines.

Once you have a handler, ``tangos add --handler=mymodule.MyHandler`` uses it,
and the name is stored with the simulation, so every later command finds it
without being told again.
