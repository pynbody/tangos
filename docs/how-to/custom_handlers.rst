Reading simulations with yt or your own code
============================================

tangos never reads simulation files itself. Whenever it needs particle data, or
the list of timesteps and halos in a simulation, it asks an *input handler*: a
class that knows how one simulation code and halo finder lay out their output.
The default handler uses pynbody, and handles every combination listed in
:doc:`/reference/simulation_formats`.

You choose a handler once, when you add the simulation:

.. code-block:: bash

   tangos add my_simulation --handler=yt.YtInputHandler

tangos stores the handler's name with the simulation, so every later command --
``link``, ``write``, ``load()`` from python -- uses it without being told
again. Different simulations in one database can use different handlers.

This page shows how to use the yt handler that ships with tangos, and then how to
write a handler of your own for data that neither pynbody nor yt can read.

.. note:: Before you start, make sure tangos is installed and knows where to find
 your simulations; :ref:`installation` and :ref:`configuration` cover both. The
 yt section builds a database from raw simulation output, so it needs yt (version
 3.4.0 or later) and the simulation files it describes. The second section needs
 no simulation files at all: its handler makes up the data it reports.

.. _using_with_yt:

Using yt instead of pynbody
---------------------------

As a demonstration, this section reads the ChaNGa tutorial simulation through
yt rather than pynbody.

Getting the simulation data
^^^^^^^^^^^^^^^^^^^^^^^^^^^

Download the `raw simulation data
<https://tangos.pontzen.uk/tutorials/tutorial_changa.tar.gz>`_.
Unpack the tar file either in your home folder or the folder that you pointed
the ``TANGOS_SIMULATION_FOLDER`` environment variable to.

Finally, download the `tutorial_changa_yt
<https://tangos.pontzen.uk/tutorials/tutorial_changa_yt.tar.gz>`_
tar. Unpack the tar file in the same folder as you unpacked
``tutorial_changa``. The ``tutorial_changa_yt`` folder contains a series of
symlinks that present the dataset with a slightly different files structure
that is compatible with yt. (Specifically, yt can't cope with the AHF files
being in the same folder as the tipsy files.)

Using yt to add a simulation
^^^^^^^^^^^^^^^^^^^^^^^^^^^^

At the unix command line type:

.. code-block:: bash

   tangos add tutorial_changa_yt --handler=yt.YtInputHandler

``--handler=yt.YtInputHandler`` requests that tangos uses yt as the "handler"
for raw simulation and halo files. The process should take about a minute on a
standard modern computer.


Verify the underlying data is being read by yt
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

For interest, you might like to check that the data really is now being handled
by yt. Open a python session and type

.. code-block:: python

   import tangos
   tangos.get_object("tutorial_changa_yt/%960/halo_1").load()

You should see that the returned dataset is indeed a yt object. If you
previously also ran the :ref:`ChaNGa+AHF tutorial <first_database>` with
pynbody, you can also verify that

.. code-block:: python

   tangos.get_object("tutorial_changa/%960/halo_1").load()

continues to return a ``pynbody`` ``SimSnap`` as before. Tangos allows
simulations loaded with different libraries to coexist.

Import some AHF-defined properties
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

At the unix command line type:

.. code-block:: bash

   tangos import-properties Mvir Rvir --for tutorial_changa_yt

This imports two properties, ``Mvir`` and ``Rvir``, from AHF's stat files, as in
:ref:`first_database`.

Add some more interesting properties
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Add a density profile using:

.. code-block:: bash

   tangos write dm_density_profile --for tutorial_changa_yt

``dm_density_profile`` is also the name of a property that is calculated using
pynbody in the :ref:`ChaNGa+AHF tutorial <first_database>`. Tangos is able to
select the correct piece of code to work with yt instead of pynbody;
:ref:`handler_properties` below explains how.

.. _writing_a_handler:

Writing your own handler
------------------------

A handler is a subclass of :class:`~tangos.input_handlers.HandlerBase`. To add a
simulation and calculate properties for it, tangos needs the handler to:

* list the simulation's timesteps, as strings -- the *timestep extensions*,
  named for being joined onto the simulation's path to find each snapshot
  (:meth:`~tangos.input_handlers.HandlerBase.enumerate_timestep_extensions`);
* give each timestep its time and redshift
  (:meth:`~tangos.input_handlers.HandlerBase.get_timestep_properties`). The time
  puts the timesteps in order, and ``tangos write`` needs the redshift;
* list the objects in each timestep
  (:meth:`~tangos.input_handlers.HandlerBase.enumerate_objects`), yielding five
  numbers for each: its position in the halo finder's catalogue (its *finder
  offset*), the finder's own label for it (its *finder id*), and its numbers of
  dark matter, star and gas particles;
* load a whole timestep
  (:meth:`~tangos.input_handlers.HandlerBase.load_timestep_without_caching`;
  tangos caches the result for you);
* load one object (:meth:`~tangos.input_handlers.HandlerBase.load_object`), given
  its finder id and finder offset.

To build merger trees with ``tangos link``, or match objects between
simulations with ``tangos crosslink``, the handler also needs a
``match_objects`` method. :class:`~tangos.input_handlers.HandlerBase` does not
define one, so without it those two commands fail; the pynbody and yt handlers
each implement their own.

100 and 150 halos. It reads no files: where a real handler would return particle
data, it returns a string describing what it would have loaded.

A few things in it need explaining:

* ``self._extension_to_filename`` is provided by
  :class:`~tangos.input_handlers.HandlerBase`: it joins the simulation folder,
  the simulation's name and a timestep extension into the path of that
  timestep's files.
* tangos never calls ``load_timestep_without_caching`` directly. It calls
  :meth:`~tangos.input_handlers.HandlerBase.load_timestep`, which calls yours
  only if that timestep is not already loaded; ``load_object`` above does the
  same, so the snapshot is read once however many objects are loaded from it.
* ``enumerate_objects`` can ignore ``min_halo_particles``: tangos itself leaves
  out objects with fewer particles than ``tangos add --min-particles`` asks for,
  using the counts you yield. The argument is there for a handler that can save
  time by skipping small objects early.
* ``match_objects`` returns a dictionary that maps the finder id of each object
  in the first timestep to a list of ``(finder id, weight)`` pairs in the
  second. A real handler works out which objects share particles, and uses the
  fraction of particles they share as the weight; this one simply links each of
  the first 100 halos to the halo with the same finder id, with weight 1.
  ``tangos link`` passes ``halo_min`` as 0, and ``halo_max`` as the number given
  to ``tangos link --hmax``, or ``None``; they ask the handler to limit how many
  objects it matches, and a handler is free to ignore them.

.. note::

   :meth:`~tangos.input_handlers.HandlerBase.load_object` names its third
   parameter ``catalog_pos`` in :class:`~tangos.input_handlers.HandlerBase`,
   but every handler that ships with tangos, and every caller, uses
   ``finder_offset``, as here. tangos passes it by position, so either name
   works.

.. The catalog_pos/finder_offset mismatch is a stage 6 item in KNOWN_ISSUES.md;
   remove the note above when it is fixed.

Your handler in action
^^^^^^^^^^^^^^^^^^^^^^

Save the code above as ``myhandler.py`` in a folder on your python path. Then,
from the shell:

.. code-block:: bash

   tangos add test_my_handler --handler=myhandler.MyHandler
   tangos link --for test_my_handler

The first command creates the simulation, asking your handler for its timesteps
and then for the halos in each: you will see 100 halos added to
``my_timestep_1`` and 150 to ``my_timestep_2``. The second calls your
``match_objects`` for the pair of timesteps, in both directions. Back in python:

.. code-block:: python

   import tangos
   halo = tangos.get_object("test_my_handler/my_timestep_2/halo_10")
   print(halo.previous.load())

prints ``Data for <your simulation folder>/test_my_handler/my_timestep_1 halo 10``.
You fetched halo 10 of the second timestep, followed the link that ``tangos
link`` made back to the first, and asked to load the underlying data, which
tangos passed to your ``load_object``. The link exists because your
``match_objects`` reported it; for halos 101 to 150, which it never mentions,
``halo.previous`` is ``None``.

tangos numbers the halos in each timestep from 1, in order of decreasing particle
count. The pretend halos get smaller as their finder id increases, so here halo
10 has finder id 10. In general the two differ; ``tangos add --no-renumber``
instead numbers each object by its finder offset, its position in the
catalogue.

Properties that need your handler
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

A property calculation that reads particle data has to know what kind of object
it will be given, so it declares the handler it works with:

.. literalinclude:: ../examples/myhandler.py
   :language: python
   :pyobject: MyProperty

Two lines make this different from the properties in :doc:`/tutorials/custom_properties`.
``works_with_handler`` restricts the class to simulations read by ``MyHandler``,
so ``calculate`` is only ever given a ``MyDataObject``; the ``assert`` is there
to show it. ``requires_particle_data = True`` asks tangos to load the object's
data at all: without it, ``calculate`` is given ``None``, since tangos skips
loading for properties that are worked out from other properties alone.

Several classes can provide the same property name for different handlers.
That is how ``dm_density_profile`` works with both pynbody and yt: when you
``tangos write`` a property, tangos picks the class that matches the
simulation's handler. ``tangos list-possible-properties`` shows which handler
each class is for.

Put the class at the end of ``myhandler.py`` and calculate it from the shell:

.. code-block:: bash

   tangos write my_fantastic_property --for test_my_handler

Then, in python, ``tangos.get_object("test_my_handler/my_timestep_1/halo_5")["my_fantastic_property"]``
returns ``42.0``.

Keep ``myhandler.py`` importable wherever the database is used, not only where it
is built: tangos imports a simulation's handler even to read stored values, since
the handler decides which property class interprets them. Without it, reading
``my_fantastic_property`` fails with ``ModuleNotFoundError: No module named
'myhandler'``.

(The tangos repository keeps this example as
``docs/examples/myhandler.py``, and its test suite runs every command on this page
against it.)

Going further
^^^^^^^^^^^^^

Other methods of :class:`~tangos.input_handlers.HandlerBase` are optional, each
enabling one more part of tangos:

* :meth:`~tangos.input_handlers.HandlerBase.get_properties` returns properties of
  the whole simulation, stored when it is added; the pynbody handler records the
  simulation's approximate spatial and mass resolution this way.
* :meth:`~tangos.input_handlers.HandlerBase.available_object_property_names_for_timestep`
  and :meth:`~tangos.input_handlers.HandlerBase.iterate_object_properties_for_timestep`
  expose values the halo finder already computed, for ``tangos import-properties``.
* :meth:`~tangos.input_handlers.HandlerBase.load_region` loads a region around an
  object, for properties that need particles beyond the halo itself.
* :meth:`~tangos.input_handlers.HandlerBase.load_tracked_region` loads the
  particles of a tracker (see :doc:`/tutorials/tracking`).
* :meth:`~tangos.input_handlers.HandlerBase.best_matching_handler` lets a
  handler hand over to a more specific subclass once it has looked at the files.

The ``mode`` argument that the loading methods receive is whatever the user gave
to ``tangos write --load-mode`` (see :doc:`/how-to/parallel`); a handler that
supports no special modes, like this one, can insist that it is ``None``.
