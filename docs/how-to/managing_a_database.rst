.. _managing_a_database:

Managing a database
===================

A tangos database grows one command at a time: ``tangos add``, ``link``,
``import-properties`` and ``write`` each add to it, often over weeks and from
several machines. This page shows how to see what went in, undo or delete what
you no longer want, and merge, compare and back up whole databases. (To list
the simulations, timesteps and properties a database holds, see
:doc:`/tutorials/quickstart`.)

.. note:: The examples that only *read* the database run here against the
 tutorial database (see :ref:`installation`); everything else changes the
 database, so is shown but not run. To try those safely, work on a copy:

 .. code-block:: bash

    cp ~/tangos_data.db ~/scratch.db
    export TANGOS_DB_CONNECTION=~/scratch.db

 ``tangos rollback``, ``delete-properties`` and ``thin-timesteps`` list what they
 will delete and ask you to confirm; ``--force`` skips the question.
 ``tangos remove-duplicates`` does not ask.

.. _runs:

Seeing what went into a database
--------------------------------

Every command that adds to the database is recorded as a *run*, along with
everything it created. ``tangos recent-runs`` lists the most recent. Here are the
last four runs that built the tutorial database, which between them added the
RAMSES simulation:

.. ipython::

 In [1]: !tangos recent-runs 4

Each run records its command line, the machine and user that ran it, when, and
how much it added. The *run ID* is what you give the commands below to act on a
run.

A parallel command can appear as several runs, one for each process that wrote
results; the tutorial database's ``tangos write contamination_fraction`` for
each ChaNGa simulation, for example, appears six times. ``tangos grep-run-ids``
finds runs by any part of their command line:

.. ipython::

 In [1]: !tangos grep-run-ids "write contamination_fraction --for tutorial_changa"

That found twelve runs, not six, because the text also matches the commands for
``tutorial_changa_blackholes``: the match is on any part of the command line. Make
the text specific enough to match only what you mean, and check with ``tangos
grep-runs``, which prints the full details of each match, before acting on a
list.

From python, :func:`tangos.all_creators` returns every run. To find which run
wrote a particular value, fetch the stored property itself, rather than its
value, with :meth:`~tangos.core.halo.SimulationObjectBase.get_objects`; it
records its ``creator``:

.. ipython::

 In [1]: import tangos

 In [2]: halo = tangos.get_object("tutorial_changa/%960/halo_1")

 In [3]: profile = halo.get_objects("dm_density_profile")[0]

 In [4]: profile.creator.id

 In [5]: print(profile.creator.command_line)

The tutorial database was built by tangos' own build script, which is why its
command lines differ in detail from those in :doc:`/tutorials/first_database`.
They also show no ``--backend``: tangos removes that option from the command
line before anything else sees it, so a run's record does not say whether it
ran in parallel.

.. _rollback:

Undoing a run
-------------

``tangos rollback`` deletes everything a run created -- simulations, timesteps,
objects, properties and links -- along with the run itself. Give it one or more
run IDs; with none, it rolls back the most recent run:

.. code-block:: bash

   tangos rollback 52

To undo a parallel command, roll back all of its runs. ``tangos grep-remove``
does so in one step, for every run whose command line contains the text you
give; it lists them first and asks you to confirm.

A run removes its results from every simulation it touched. A ``tangos write``
without ``--for``, for example, writes to every simulation in the database, and
rolling it back removes all of those results, not just one simulation's.

Rolling back a run removes exactly what that run created, and nothing that later
runs built on it. So to remove a whole simulation, roll back *all* of its runs,
newest first, ending with the ``tangos add`` that created it. For the RAMSES
simulation, whose four runs were listed above, that is:

.. code-block:: bash

   tangos rollback 52 51 50 49

Find all of a simulation's runs with ``tangos grep-runs`` and the simulation's
name -- remembering that a run without ``--for`` will not mention it, and that
the name may also match other simulations.

Rolling back only the ``add`` would delete the simulation and its objects but
leave behind the properties and links that the later runs attached to them,
taking up space with nothing to reach them; no command cleans these up
afterwards. Nor is there a ``tangos`` command that removes a simulation
directly.

.. The orphans left by rolling back an early run, and the missing remove
   command, are a stage 6 item in KNOWN_ISSUES.md.

Deleting properties
-------------------

To remove a property, whichever runs wrote it, use ``tangos delete-properties``:

.. code-block:: bash

   tangos delete-properties uvi_image --for tutorial_changa/%960

``--for`` takes a simulation, a timestep or a single object, as in
:ref:`concepts`; without it, the property is deleted from the whole database.
You can name several properties at once.

Writing a property again
------------------------

``tangos write`` skips any object that already has the property, so to replace
values -- after fixing a bug in your own property calculation, say -- add
``--force``. The new values are stored *alongside* the old ones rather than
replacing them, and until you remove the old copies, reading the property with
``halo["name"]`` returns both, as a list. Once the new values are in, remove the
old ones with:

.. code-block:: bash

   tangos remove-duplicates

which keeps the most recently written value of every property on every object,
and the most recent copy of any link written more than once. It applies to the
whole database. Alternatively, delete the property first and then write it
without ``--force``.

Thinning out timesteps
----------------------

A simulation may have far more snapshots than you need. ``tangos
thin-timesteps`` removes timesteps until consecutive ones are at least a given
time apart, in Gyr:

.. code-block:: bash

   tangos thin-timesteps 2.5 --for tutorial_gadget

It works forwards from the first timestep, removing each that comes less than
2.5 Gyr after the last one it kept, and lists what it will remove before asking
you to confirm. For the eleven timesteps of ``tutorial_gadget``, it keeps five.
With ``--relative``, the interval is instead a fraction of the mean spacing
between timesteps.

Removing a timestep removes everything in it, including the links that join it
to its neighbours, and nothing remakes those links. Thin a simulation straight
after ``tangos add``, before ``tangos link``; if you thin it later, run
``tangos link`` again (which needs the simulation data) to join the timesteps
that are now adjacent. Running ``tangos add`` for the simulation again would add
the removed timesteps back.

.. _merging_databases:

Merging databases
-----------------

``tangos import`` copies the whole of one or more other databases into the one
``TANGOS_DB_CONNECTION`` names:

.. code-block:: bash

   tangos import simulation_a.db simulation_b.db

This lets you build each simulation in its own sqlite file -- in separate cluster
jobs, say, with no contention for one file -- and combine them at the end. The
sources can be sqlite files or the URLs of database servers, and
``--exclude-properties`` leaves named properties behind (see
:doc:`/how-to/database_backends`, which uses the same command to move a sqlite
database onto a server).

``tangos import`` copies; it does not merge objects that both databases
contain. Importing a simulation that is already present adds a second
simulation of the same name, after which looking it up by name fails with
"Multiple matches". Only import databases whose simulations are new to the
target.

Comparing databases
-------------------

``tangos diff`` reports how two databases differ: simulations, timesteps or
objects present in one but not the other, and properties whose values differ.

.. code-block:: bash

   tangos diff simulation_a.db rebuilt.db --simulation tutorial_changa

``--simulation``, ``--timestep`` or ``--object`` restricts the comparison;
without one it covers everything. Within each timestep, it compares the
properties of the first ten objects of each type, not every object.
``--ignore-value-of`` names properties whose values should not be compared, and
``--property-tolerance <name> <rtol> <atol>`` sets how closely a property's
values must agree (by default, :math:`10^{-3}` for both; set by
``diff_default_rtol`` and ``diff_default_atol`` in :ref:`configuration`). It exits with status 1 if it
finds a difference, so scripts can act on the result; tangos' own continuous
integration uses it to check each newly built test database against a
reference copy.

Moving the simulation files
---------------------------

The database records where each simulation's files are only relative to
``TANGOS_SIMULATION_FOLDER``. If you move the whole folder, set the variable to
its new location and everything carries on working; only moving simulations
within it, or renaming them, breaks the connection to their files. Querying
stored values needs no simulation files at all.

Backing up
----------

A sqlite database is one file: copy it while nothing is writing to it. For a
database server, use the server's own tools (``mysqldump``, ``pg_dump``), or
take a sqlite copy of it with ``tangos import``, pointing
``TANGOS_DB_CONNECTION`` at a new file just for that command:

.. code-block:: bash

   TANGOS_DB_CONNECTION=backup.db tangos import postgresql+psycopg2://tangos:my_secret_password@localhost/database_name

.. seealso::

   :doc:`/how-to/database_backends` for moving to a database server,
   :doc:`/how-to/large_simulations` for keeping a database's size down, and
   :doc:`/how-to/parallel` for building one quickly.
